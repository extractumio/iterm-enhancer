# v0.35.0 — A lighter load on iTerm2, and a trace for coding agents

## What changes

- **iTerm2 stays responsive.** The bridge asked iTerm2 about 13,000 times a minute, and
  iTerm2 writes every answer out for its Script Console on its main thread, so screens, keys
  and history in the web app waited for seconds at a time. The bridge now asks about a third
  as often, with half the data: closure tracking skips what cannot have changed, the session
  list asks a pane's details in one request and reads an agent's screen only when its title
  changes, the theme reads only its colors. `bridge.log` has a line a minute with the
  bridge's calls by source.
- **"iTerm2 is not responding".** When iTerm2 does not answer for 3 s, the web app says so
  above the terminal and counts the seconds, until it answers.
- **A context trace for coding agents.** Open the web app with `?trace=2`, reproduce a
  problem and press **trace** (left of ⓘ): the page's last events and its state are copied
  as text to paste into a coding agent's chat. It stays in the page until you copy it. The
  format and how to analyse a trace: `docs/web-trace.md`.
- **↓ in an agent's input** goes on after a space typed at the end of a paragraph (it did
  nothing).
- **Paths in a coding agent's tool output** no longer show a space where Claude Code cut the
  line at the window's edge ("…/e nv").
- **Bookmarks** mark their whole text with the wavy line, not only the first part.

## Upgrading

Run `~/.iterm-enhancer/bin/iterm-enhancer upgrade`. Open web app pages reload themselves, and
you stay signed in.

## Validation

The bridge's call counter on a Mac with 22 sessions and a page open: 13,375 calls and 10.5 MB
a minute before, about 4,400 calls and 5.3 MB after, with no API timeouts since. Rust,
Python and UI unit tests pass, with new ones for closure tracking's reads, the counter and
the "not responding" check; the browser checks pass in Chromium and WebKit, with new ones
for the trace, ↓ after a typed space, a tool's output cut inside a path, the "not
responding" line and a long bookmark; each new check fails without its fix. Not checked
against a live iTerm2: closing a tab, Undo and restore after the closure-tracking change
(the unit tests play them).
